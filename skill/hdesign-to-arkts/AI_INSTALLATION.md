# 交给 AI 的覆盖安装指南

适用于将旧版 hdesign-to-arkts 更新为本仓库的 **v2.3-sdk**。只处理本 skill 和明确获准接入的规划规则；不顺带安装两个 DSH 插件或升级宿主。

## 可直接复制的安装请求

> 请把 Alentaoker/dsh-harmoneydev-tools 中 skill/hdesign-to-arkts 覆盖安装到我当前 AI 宿主实际使用的同名 skill 位置。先读取该目录 INSTALLATION.md、AI_INSTALLATION.md 和 CHANGES.md，记录来源提交。确认宿主实际加载路径，备份旧目录；将新目录完整准备好后替换，不能合并复制留下旧 dHash、社区库或浏览器取参文件。保留我的项目专用 SDK 索引并核对新格式，不能用随包 API 26 快照静默覆盖。核对安装后文件、脚本与宿主发现状态。若目标路径或本地定制无法判定，展示具体差异再问我。不要改其他 skill、MCP 配置、工程代码或插件。报告安装位置、备份位置、所用 SDK 索引、完成项和需要重新加载的事项。

如果还需要自动衔接现有 grill/plan，再追加：

> 同时将本 skill 的“规划流程接入约定”增量接入我正在使用的需求澄清/plan 规则。先定位实际生效文件并保留其他内容；不要创建一套平行规则，也不要重复追加已有约定。

用户已授权覆盖安装后，以下备份、准备、替换和检查可继续执行，不为同一安装步骤重复求批准。只有路径不明、定制冲突或新增授权范围需要用户选择。

## 1. 明确来源与生效位置

记录仓库提交/tag、源目录、宿主名称/版本，以及当前同名 skill 的加载路径。以宿主技能管理、配置或实际加载来源为证据，不把某个磁盘上的同名文件当作生效版本。

检查系统级、用户级、项目级是否存在重复副本及加载优先级。找到多个副本时先确认当前生效者；不要把全盘同名目录都覆盖。目标路径无法确定时，把候选路径与依据交给用户选择。仅此部分待确认，仍可准备来源文件。

安装源必须包含 `SKILL.md`、其引用的 `references/`、两个查询/构建脚本、catalog/source 两份 JSON，以及本目录使用文档。来源仓库有未提交改动时保留现场，使用已确认提交的独立副本，不 reset/clean。

## 2. 备份与整理本地定制

将旧 skill 完整备份到**宿主不会扫描的备份目录**，记录位置与时间。备份也包含 SKILL.md，不要放在会递归发现技能的目录内，以免同时加载新旧版。

比较旧目录，区分：旧版规则/脚本、用户定制规则、目标工程 SDK 索引及来源。用户定制不静默丢弃；与新规则不冲突时在新目录增量保留，冲突影响结果时列差异询问。

项目专用 SDK 索引不能被随包快照覆盖：

- 新 schema 为 `hdesign-sdk-symbol-catalog-v1`；符合新格式、来源可追溯且仍适合目标工程的索引可保留并核对。
- 旧社区合并库、图片 hash 库或来源不清的索引只保留在备份中，使用目标 SDK 重建；不能仅改文件名或 schema 冒充兼容。
- 没有目标 SDK 时，可安装规则与查询脚本，但将项目资源映射标为待准备；不能宣称随包版本已适配公司工程。

## 3. 准备完整的新目录

在技能扫描范围外准备暂存目录，复制**源目录内容**，检查不是 `hdesign-to-arkts/hdesign-to-arkts/SKILL.md`。只带发布文件，不带实验报告、验证结论、截图、字体二进制、会话记录、缓存或本地凭据。

不要从旧目录带回 `match-symbol.ps1`、dHash/图片索引、社区 symbol 库、浏览器 DOM 取参规则或旧自动矢量匹配流程。也不要靠新增文件覆盖同名文件后，假设旧文件会自动消失。

读取新 SKILL.md 确认入口名称仍为 `hdesign-to-arkts`。在暂存目录核对 Markdown 相对链接、catalog/source 来源与 catalog SHA256；通过脚本的 `--help` 确认参数。查询脚本只需 Python 标准库；索引重建单独处理 fontTools 依赖。

## 4. 替换本 skill

暂停使用该 skill 的当前开发操作，防止一次任务混用两版规则。替换前解析源、目标与备份的绝对路径，确认目标是已选技能根目录下的 `hdesign-to-arkts`，不是技能根目录本身，也不是其他目录；遇到链接/重解析点先明确实际目标。

使用同一文件操作工具完成备份与替换。Windows 优先用 PowerShell 的 `-LiteralPath`，不跨 shell 拼接删除命令。保留独立备份后，将旧同名目录移出扫描范围，再把准备好的新目录放到原路径。不要递归清空整个 skills 根目录。

任一步失败就停止后续切换，记录当前源/目标位置；利用备份恢复本 skill。不能在部分文件已更新时报告完成，也不要为了恢复覆盖用户其他配置。

## 5. 按授权接入上游规则

仅在用户同时授权时，找到正在使用的 grill/plan skill 或项目规则，把 [规划流程接入约定](references/checklist-template.md#规划流程接入约定) 增量加入。先备份对应文件，合并已有同义规则，保留用户其余约定。

接入内容要表达：识别 UI 变化、对应区域开发前取参、目标歧义时询问、记录图标处理、禁止 Pixso 转代码、纯逻辑不强制取参。不能只加一句“必要时用 skill”就宣称能防止跳步骤。没有该授权则提供这段约定，不修改上游文件。

## 6. 安装后检查

1. 检查新目录完整，旧识别脚本和旧规则未残留；本地定制与专用索引按已决定方式处理。
2. 使用实际 Python 执行 `scripts/lookup-symbol.py --help` 和一次精确名称/字码查询，记录实际索引来源；不要把某次查询成功当作设计映射已正确。
3. 按宿主方式重新加载技能/开启新会话，确认同名 skill 发现且读取新路径；当前会话无法刷新时明确写“文件已更新，待重新加载”。
4. 核对宿主是否具备 Pixso MCP 工具；若有已打开设计，可做只读连接检查。缺连接时记录待配置，不私自修改 MCP 服务。
5. 不为安装演示导入/修改设计稿，不调用转代码，不导出未批准图标，不修改鸿蒙项目代码。

这些是本地安装检查步骤；检查记录留在本机或当前对话，不加入发布仓库。

## 7. 交付与恢复

交付时列出来源提交、实际安装目录、备份目录、保留/重建的 SDK 索引、上游规则是否修改，以及宿主发现/MCP/依赖的实际状态。将“文件已替换”“宿主已加载”“设计已取参”分开表述。

需要恢复时，先保留失败的新目录，再将备份中的旧 skill 恢复到原生效路径；上游规则只恢复本次改动，保留用户后续新增内容。重新加载宿主，核对实际生效来源，不删除其他 skill、工程资源或 DSH 数据。
