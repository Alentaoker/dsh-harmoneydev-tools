# RAR 与 GZ 编码修复（2026-10-17）

配套 Harmony 0.5.0-rc.5 / E2E 0.4.0-rc.5。修复版本升级前的既有 RAR 未接入及 GZ 文本严格 UTF-8 失败。

## 原因与行为

- 旧版仅识别 ZIP/GZ，RAR 被走到文本导入。新增 RAR4/RAR5 路径，使用随 npm lockfile 固定的完整 7-Zip 26.04，无需另装 WinRAR；仅经 stdout 输出选定日志，插件写入自己的受限暂存路径，不运行档内程序。
- GZ 是压缩格式，解压后可能是 UTF-8、UTF-16、GB18030 文本或原厂编码 HiLog。旧版本只探测头部 8 KiB，后续正文仍严格 UTF-8，前段正常而后段异常会失败。
- 自动识别 BOM、UTF-16 字节序和 UTF-8/GB18030；UTF-8/GB18030 检查整个文件，避免长 ASCII 前缀掩盖后段编码。可在导入旁手动选编码，重新解析压缩文件时也采用当前选择。
- 不可还原的少量字节使用替换字符并明确提示数量；原始字节保留，不把异常内容静默当完整解析。乱码可换编码重新解析/导入。
- 原厂 HiLog 的 GZ 仍需官方 hilogtool 与配套 hilog_dict*.zip；绝不把二进制直接当作可读日志。官方解码输出可能含少量异常字节，此时保留可读部分并标记 partial。
- RAR 加密、缺分卷、损坏、链接、歧义路径、大小写冲突和超量条目会明确拒绝，原包保留；支持单份明文 256 MiB / 压缩包 512 MiB / 累计展开 2 GiB，清单 16 MiB、10000 条。

## 证据

使用此前从当前手机实际采集的 13545 行日志原字节封装为 RAR4/RAR5（存储模式），分别导入均保留 13545 行；同一批内容无损转换为 UTF-16LE、UTF-16BE、GB18030 和 UTF-8 后做 GZ，均正确识别，替换计数为 0。没有生成或循环填充日志；这是同一真实内容的容器/编码兼容检查，不是额外采集的新日志。

4 份原厂设备 GZ 配套字典实际官方解码共 147576 行；存在 unknownlog，维持 partial。其中一份有 3 个替换字符，明确显示警告，不冒充完整还原。用户本次报错的两份原文件尚未获得，因此不宣称已针对这两份文件复现通过。

自动检查覆盖 RAR4/5、原包字节保持、路径/链接/加密/重复/大小限制、UTF-16 GZ、64 KiB 以后才出现 GBK 和异常 UTF-8、显式编码及重新解析；默认数据路径测试改为独立临时 profile，避免读取或写入用户日常数据。

## 使用

升级并完整退出、重启 DSH 后，工作台导入旁应出现“自动识别编码”；文件选择允许 .rar。先用自动，出现乱码再选择 GB18030/GBK 或对应 UTF-16 字节序。旧版失败记录如仍为原包，可点重新解析；重新解析保留原包，旧正文替换副本进入回收区。

## 安装与界面验收

已备份并登记 desktop/web 到新的长期来源目录，实际桌面从应用菜单正常退出、同 DataHome 冷启动，显示 E2E 0.4.0-rc.5。网页版实际选择 RAR5、UTF-16LE GZ、GB18030 GZ，队列 3/3 完成，各 13545 行；正文标题显示编码，范围与完整性显示转换说明。没有发送模型消息。

原生 Windows 文件对话框已显示 .rar 允许类型，但自动化无法稳定定位其子窗口，原生选择文件完成链路未计通过；网页版同一后端的完整导入已验证。桌面冷启动检查与网页版导入证据分别记录。

代码与自动回归包括 59 项 E2E 检查及 3 项发行/登记脚本检查；Harmony 未作运行源码变更。用户原始两份报错文件尚待路径补充。
