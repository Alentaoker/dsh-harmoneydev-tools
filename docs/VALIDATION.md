**当前边界：**桌面原生“打开文件”对话框可以出现，但 Computer Use 无法定位其编辑控件，因此该选择器的自动导入未完成。完整导入链路由真实组件、实际 HTTP 路由和磁盘库验证，不能冒充桌面文件选择器已验。此次日志验收未运行新的小艺 Work AI 任务，早期失败/成功记录见下文。

真实设备高流量时观察到入口队列省略及缓冲淘汰，界面明确显示数量；实时窗口不是完整历史。Harmony 保留上限为 10000 行及计数文本 8 MiB；这不是整个 DSH 的内存承诺。E2E 每次测试默认磁盘容量 32 MiB、内存尾部 1000 条/2 MiB；离线文件上限 32 MiB，结构化副本 64 MiB，页面至多 100 行/约24 KiB，长行明确提示。

100000 行隔离磁盘查询约 186ms，返回 69 行/24075 字节，独立 Node 进程 RSS 77.32→79.18 MiB、heapUsed 11.11 MiB。它只说明该查询实验有界，**不是 DSH 总内存或所有文件的性能保证**。Windows ARM64、其他宿主、macOS/Linux、所有设备版本和长期稳定性仍待单独验证。

**实机失败保留：**“设置只读”任务执行 home、点击设置、页面断言，约 38.3 秒后未通过。实际结束截图为空白应用页面，断言未找到“设置”。采集状态 captured，保留 513 条目标日志；两张边界截图和运行器失败证据已保存，控制释放为 true。不仅凭日志级别判断应用内部原因。

**调整路径通过：**从失败报告的“调整后复测”带入参数，明确缩小目标为返回桌面、验证设置图标，关闭本次通用检查的应用日志采集，并同步修改确定步骤。生成会话草稿后发送，调用 retry 生成新记录，约 17.8 秒通过，控制释放为 true；原失败报告保留，parentRunId 关联正确。日志 disabled／0 条是预期行为，不能作为应用无异常的证据。此通过项不代表原设置页面问题已修复。

旧小艺会话只显示自己的 3 条记录，新验收会话只显示自己的 2 条记录。模拟测试另外覆盖 42 条历史记录的分页、跨会话拒绝、归档正文保留，以及重启中断标记。桌面端确认实际显示开始前／验收后截图；通过下载入口保存一张 PNG，文件哈希与报告原图一致。

验收发现并修复了原文件接口未声明 requestBody 的问题：宿主把 bodyless GET 当作 streaming 请求，导致截图和导出不可用。接口现声明 buffered，并由注册契约及真实 PNG 路由测试覆盖。客户端使用临时对象 URL 读取图片与下载，离开页面释放图片引用。

仍未验证或实现：长期手机功耗／所有设备兼容、实机强制断线与宿主崩溃后的完整恢复、完整小艺 Work 自主流程、截图差异比较、独立用例库和批量调度。取消与重启状态的本次新增验收主要为模拟测试；不要解释成所有手机流程均已稳定。旧原生视频 CI 提交 `14287c5` 的 Windows 全新构建与测试已通过；本次提交以自己的 Actions 运行结果为准。

## 0.3.0 原生视频改造

- 组件原字节内嵌到插件，哈希核对通过。测试将 DevEco Testing 环境路径设为不存在的位置，仍从插件自身资源打开真实 H.264；运行时没有双层 JAR 解压或 Java sidecar。

- 修复原生参数连写被忽略的问题。四轮实机测试均收到真实 H.264，静止 16 秒仍存活，关闭清理 complete；最后一轮为均衡档重新连接。

测试在手机设置页执行六次往返滑动。传输量包括协议封装，随页面动画和内容变化，不是恒定码率或所有场景的性能保证。单个 native callback/picture packet 不能当作浏览器显示帧率。

独立资源加载探针：旧代码四次约 299–386 ms，加载前/后 RSS 49/210 MiB；新代码首次约 2 ms，后续 0.25–0.31 ms，RSS 41/42 MiB。**这里只测资源读取进程，不是整个 DSH 的内存或持续投屏 CPU。** 视频探针 RSS 约 69–74 MiB，也不代表桌面端总占用。手机端进程采样未取得可靠值，未给出手机 CPU/内存结论。

桌面端已实际显示“实时视频流 · 636×1430”，状态为 streaming，组件哈希匹配，均衡参数确认；不是 JPEG 预览。质量设置中可看到三档。页面隐藏和恢复、缓冲边界、几何守护另外有模拟测试。

新版本 Harmony 测试 53/53，E2E 测试 12/12 通过；Windows 全新 CI 以本提交运行状态为准。尚未做长时间功耗、不同设备、实际显示 fps 测量、同时预览与录像共享编码验收，也没有重跑完整小艺 Work 自主任务。

## 真实手机

设备：一台 API 24 的 HarmonyOS 手机，USB/HDC 在线。没有锁屏密码；识别应用来自设备包管理信息，不硬编码设备序列号。

- 曾通过 dshE2E 进入并独立确认“小艺 Work”页面，之后切换文字输入、提交三条学习安排请求，返回实际正文并通过独立验收。文本阶段约 72 秒，5 次模型调用。
- 该早期成功任务没有绑定日志目标，因此应用日志为 0；它不能作为日志采集成功的证据。
- 日志修复前的验收 A 仅保存 3 条，其中有缓冲历史条目，界面验收还被错误的 executor verdict 分类遮挡。两处均修复，并保留本机失败报告。
- 修复后的验收 B：目标应用、进程、日志流和设备日志时间水位均确认，持续采集成功；保留最近 1000 条，外层 AI 调用 `get_logs` 读到了真实正文。该次界面流程仍因派发前目标离开屏幕而失败，不能宣称全流程通过。
- 针对上述派发前失效增加最多两次重新观察；只有运行器明确说明尚未派发的错误可恢复，不自动重放未知效果的动作。该恢复已通过模拟测试。
- 最终复测 C：没有再以相同旧控件错误直接退出，任务约 104 秒后因模型调用预算耗尽停止，**UI 验收未通过**；日志状态为 captured，保留最近 1000 条，设备控制已释放。这说明采集链路可用，不说明自主操作已经全面稳定。
- 复测后在 0.1.2 修正了恢复记录占用模型预算的计数问题，以及日志进程刷新阻塞界面观察的问题。以真实调用次数计数的测试已通过；这两个最后改动尚未重新执行完整的小艺 Work 实机任务，不能宣称已解决所有自主操作问题。
