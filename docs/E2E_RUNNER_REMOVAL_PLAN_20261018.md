## 2. 目标架构与用户工作流

```text
当前 DSH 会话 AI
  ├─ 分析日志、源码、需求；实施修改；提出可观察检查点
  ├─ 保存开发任务和安装交接 → 结束该轮，等待用户安装
  └─ 用户确认已装好 → 选择验证模式 → 调用 Harmony → 依据新证据给出检查结果

dshHarmony：唯一设备执行/观察层
  ├─ 短期控制租约、现有驱动与互斥、目标新鲜度/坐标校验
  ├─ 只读观察与截图、结构化工具回执
  └─ 自动把实际调用与观察写入当前验证轮次；独立日志采集

dshE2E：被动开发任务/验证轮次/证据服务
  ├─ task + attempt + append-only events + evidence + CaptureSession
  ├─ 现有日志工作台、Trace/历史界面、检查点与安装交接
  └─ 双读单写：legacy-e2e-v1 只读；validation-v1 写入
```

### 2.1 从日志修 Bug

1. 用户提供日志地址/文件、Bug 现象、可能的代码位置；代码位置只是线索，先对照日志分析。
2. 当前 AI 修改源码，保存改动摘要、涉及文件、待验检查点和安装交接 revision；任务状态为“等待安装”，本轮结束。
3. 用户手动编译安装并回复“已装好”。记录确认来源，再选择“AI 操作验证”或“我操作，AI 观察分析”。
4. 创建新 attempt，采集真实设备信息/观察/日志，逐项记录结果；发现问题后再修改则回到“等待安装”。

### 2.2 从需求做功能

需求 → 可观察检查点 → 当前 AI 实现 → 保存交接并结束 → 用户安装确认 → 新轮验证。只验收已安装功能可直接建验证轮次，不必先伪造一次代码修改。

纯本地日志分析继续直接使用日志工作台/文件工具；不强制新建 task、创建设备验证、复制导入全部文件或持有设备租约。

“等待安装”是保存后的业务状态，不能成为后台等待进程。用户“已装好”是人工声明；设备包版本读取是设备证据；源码/包是否对应另记关联可信度，三者不能合并成“已证明安装了这份源码”。

## 3. 数据、状态与最小工具契约

命名可以按现有项目风格调整，以下是职责契约，不要求为了名称再搭一层框架。

### 3.1 新数据结构

```text
dshE2E storage/
  workflows/                         # 旧数据原位保留，只读
  validation-v1/
    sessions/<安全会话键>/tasks/<taskId>/
      task.json
      attempts/<attemptId>/
        attempt.json
        events.jsonl
        evidence/                    # 脱敏图、树、工具结果引用
        logs/                        # 自有原始采集与完整性元数据
```

- session 身份从宿主可信上下文获取；不能相信模型自由填写的 sessionId，也不能把原始 session 字符串直接拼路径。沿用安全编码/哈希命名，元数据保存归属。
- task：schema/version、taskId、session、项目、bug/feature/验收类型、需求/现象、日志引用、代码线索、改动摘要、revision、检查点、安装交接、创建/更新时间。
- attempt：attemptId、taskId、taskRevision、检查点快照、ai/human 模式、设备/包信息、用户安装声明、来源关联可信度、开始/结束时间、执行状态、语义结果、日志完整性、控制清理、证据缺口。
- event：schemaVersion、单调 seq、eventId、task/attempt/revision、callId/operationId/checkpointId、事件类型、来源、hostTime、可选 deviceTime、结构化数据/错误、证据引用。每个 attempt 串行追加，不能按前端返回先后拼接伪时序。
- CaptureSession：captureId、session/task/attempt 归属、设备、目标包/进程、起止、水位线、限额、丢弃/中断、归档路径、清理状态。允许先独立采集，再通过受控操作关联同会话任务；不隐式覆盖原归属。

task 可跨修改/安装；attempt 是一次验证事实。新修订不改写旧 attempt 的检查点和结论，已有结果不能当新代码已通过。

### 3.2 状态分开保存与展示

| 维度 | 建议取值 | 不能据此推导的结论 |
|---|---|---|
| task 交接状态 | draft / awaiting-install / ready-to-verify / completed | completed 不能覆盖未验证检查点 |
| attempt 执行 | active / finished / cancelled / interrupted | finished 不等于功能通过 |
| checkpoint 结果 | pass / fail / unverified，附来源与引用 | 工具返回成功不等于 pass |
| 总体语义 | passed / failed / incomplete | 缺必验项不能 passed |
| 日志完整性 | complete / partial / interrupted / not-collected | 不直接判应用功能失败 |
| 清理 | pending / released / failed | 清理异常不能吞掉原验证结果 |

首版一会话最多一个 active attempt；同一设备互斥控制，跨会话不得混入。cancel/finish 幂等，结束后拒绝新增动作和检查结果，仅允许明确的清理尾事件。宿主重启只把新版未终结记录恢复为 interrupted，不自动继续动作。

### 3.3 六类工具职责

| 职责 | 建议入口 | 要点 |
|---|---|---|
| 保存任务/交接 | save_task | 创建/更新受版本约束的任务，保存检查点和安装交接；同一 task 更新有 revision 冲突检查 |
| 开始验证 | begin_validation | 要求任务/检查点、模式、设备，以及安装确认或明确“验现有安装”；显式返回 attemptId 和 contextRevision |
| 记录检查结果 | record_checkpoint | pass/fail/unverified、公开说明、证据引用及来源；人工声明单独标记，不写伪工具派发 |
| 结束验证 | finish_validation | 汇总检查点、停止关联采集/释放自身租约、保存清理结果；拒绝证据不全却宣告全通过 |
| 读取记录/事件/证据 | read_validation | 同时支持 legacy/new；列表和事件游标分页；不静默截断 |
| 取消验证 | cancel_validation | 停止后续动作，取消在途等待，终结自己采集与控制，保留已有事实 |

日志独立开始/停止、人工操作声明可作为上述服务的附属操作，复用既有日志/工具能力；不要为凑六个名称牺牲独立采集。是否暴露为同名子命令或少量工具按现有 agent 接口决定，保持用户侧入口少而清楚。

校验要求：task/attempt/capture/evidence 的 session 和设备一致；路径 realpath 后仍在预期根；处理软链、路径穿越、错误会话及已结束 attempt。客户端旧 HTTP session 参数必须走宿主已有可信边界，不能把 agent.exec 上下文当成所有 HTTP 请求天然拥有的身份。

## 4. Trace 与 Harmony 执行接入

### 4.1 自动事件的真实范围

首版可靠覆盖 Harmony 工具包装层和验证服务生命周期。工具开始/结束、观察、控制动作、错误、采集、检查结果、人工确认均自动或明确写入。完整宿主模型/终端/源码编辑事件只有在核对当前 SDK 真的提供后才接入；未接入显示“未采集”，不能显示零次调用、完整 AI 推理或伪造耗时/Token。

只记实际工具输入输出、公开决策摘要和证据，不记录或重建隐藏思维链。新格式从自己的事件生成，不能再依赖第三方 report.json 才显示时间线。

### 4.2 在 Harmony 包装层记录，避免 AI 手写执行事实

1. 从可信会话上下文解析 active attempt；在调用开始时固定 attemptId/revision/callId，异步完成仍写回原轮次，禁止重新读全局“当前轮次”导致串记录。
2. 调用前写 tool-start；mutating 调用必须确保可记录再派发。调用后保存结构化 result、错误、必要证据与 tool-end，不改变已有工具输出兼容性。
3. `src/index.ts` 在把错误拼为字符串之前保留 code、details、cause、stage、dispatchState、effect、verification；裁剪/脱敏有明确元数据，不能把长错误当正常结果。
4. 底层能提供的目标解析、snapshot generation/revision/quality、ref、geometry 和派发信息才写入；缺少的标 unknown，不根据“await 前后”猜 sent/confirmed。
5. 没有验证上下文的普通 Harmony 调用继续可用；明确它没有创建验证记录，不能自动宣称功能通过。

### 4.3 动作与效果必须分开

- 派发：`not-sent / sent / unknown`；效果：`confirmed / not-effective / unknown`。驱动响应成功只说明调用层事实，效果要靠新观察/回执/检查点证据确认。
- 超时、取消或 `ACTION_MAY_HAVE_COMMITTED` 后先重新观察，禁止自动重发发送消息、删除等可能已提交的动作。operationId 只防服务重复提交，不能宣称设备 exactly-once。
- `run_scenario` 仅保留短确定步骤的工具用途；不作为所有验证必经 DSL，不再隐藏另一轮自主规划。
- 同步清理 E2E `agent.mjs` 与 Harmony `agent.ts` / `task-routing.ts` 的旧提示词、help/capabilities 和错误引导。移除强制 `e2e_phone.run`、`E2E_REQUIRED` 及“内层独立 AI 验收”等过时说法。
- 路由改为验证上下文/归属协调，保留设备租约、忙碌冲突、取消与控制权保护；不能为了移除强制路由而取消底层互斥。

### 4.4 人工操作模式

- 人工模式禁止自动控制动作；只读截图/页面观察和日志不能获取自动化控制租约、重启应用或抢投屏。
- 逐一检查 observe_screen / observe_page / take_screenshot 的实际路径；当前 observe_page 直接 snapshot 是候选，不能假设其他观察入口也无租约。
- 复用底层串行器协调 driver 调用；观察并发不等于允许绕过锁。设备占用时等待/提示冲突，不停止他人镜像或夺控制权。
- 用户点击等仅记录“用户声明的动作”和之后可观察变化，不伪造自动点击回执。
- 日志跨 AI 回复继续采集；turn-stopping 不等于人工验证结束。明确结束、取消、会话关闭、宿主退出时清理自己资源。

### 4.5 图像、坐标和引用

- 保留现有脱敏与证据生成；截图缺树/脱敏失败按原安全策略处理并显示缺口，不能为显示图片绕过保护。
- 保存 nativeSize、displaySize、captureTime、orientation、coordinateSpace、geometryId 和缩放/旋转映射；当前报告图会缩到 720×1600，不能把这张图上的点当原生坐标。
- Harmony 已有 frame/native、geometryId 与新鲜引用校验，优先复用；转屏、尺寸变化、旧 ref 必须重新观察，不静默映射旧几何。
- 缺失 geometry/观察质量或图像能力时，视觉检查标未完成；节点文字存在不能冒充图片内容已目视验证。

## 5. 独立日志 CaptureSession 与关联

抽离 `logs.mjs` 的 startLogCollection 和 log archive，使其依赖专门 CaptureSession，不再依赖 runner job.controller/job.lease。保留现有能力：

- 明确目标包/进程、PID 再识别与 PID 复用保护；logAppBundle 不隐式启动应用，appBundle 原有启动语义不能混淆。
- 原始行、水位线、接收时间、设备时间、进程刷新、stream readiness、停止/取消、限额、dropped/warnings 和归档元数据。
- 单独的 AbortController 与生命周期；用户/会话结束能停；宿主恢复标 interrupted，不自动启动旧验证或采集。
- 关联 attempt 只引用同会话受控归档，不能将所有实时日志重复复制进每个事件。实时环形缓冲与验证归档的容量/完整性分别报告。
- 事件 ±2 秒只作时间邻近参考，不宣称因果；优先请求 ID、trace ID、操作 ID、应用/进程等强关联。保存主机与设备双时间轴及已知偏差，不能直接混排未校准时间。
- 当前会话日志库和跨文件搜索仍归 dshE2E 管理，独立采集不能再造一套日志工作台或新目录隔离模型。

## 6. 新旧历史与 UI

### 6.1 双读单写

- 新数据只写 validation-v1；旧 workflows、dsh-run.json、record.json、e2e/report.json、图片和日志原位只读。
- 新建 legacy adapter，禁止调用会重写 record.json 的 records.ready。旧 queued/running 可在展示层解释“历史记录未正常结束”，不修改原文件。
- legacy/new 都适配到统一 ViewModel；旧数据缺派发状态、坐标、日志完整性等显示“旧格式未记录”，不能补成 sent/confirmed/完整。
- 旧“重跑/重试/回放”入口替换成“沿用检查点新建验证”。不能执行旧 task.e2e.ts、缓存动作、report 内脚本或自动新开模型循环。
- 保留必要旧读取 API；旧执行 API/工具明确返回已退役与新入口，不能偷偷转去执行新动作。同步更新工具发现和接口能力版本，避免旧 AI 继续用旧契约。

### 6.2 精简界面，保留四类内容

1. 任务概览：需求/Bug、日志来源、改动与安装交接、当前状态、检查点，不做流程编辑器。
2. 验证时间线：公开摘要、真实工具/观察/错误、人工确认、逐项结果；点击看原始结构与证据，事件游标分页。

## 8. 检查矩阵：源码阶段与授权后阶段分开

### 8.1 本轮应编写的行为测试

| 类别 | 关键断言 |
|---|---|
| 无 runner 启动 | 不提供 e2e 包时日志/历史/新服务可加载；无旧 eager import；没有 CLI 生成和内部模型调用 |
| legacy 只读 | 读取前后旧文件内容 hash/mtime 不变；破损/缺字段可见降级；活动历史不会被改写；不执行旧配置/缓存 |
| 状态与引用 | revision 冲突、重复 begin/finish/cancel、结束后拒写、取消后不再派发；旧轮次结果不覆盖新 revision |
| 会话/设备边界 | 错 session/task/attempt/evidence、路径穿越/软链、同设备冲突、异步晚返回写回原 attempt |
| Trace 完整性 | seq 单调且不重复、分页无漏重、超长结果有引用/分页、半行恢复可见、unknown 指标不伪零 |
| 派发语义 | not-sent/sent/unknown 与 effect 独立；ACTION_MAY_HAVE_COMMITTED/超时不重发；结构化 cause 保留 |
| 人工模式 | 只读观察不获取自动控制租约；拒控制动作；用户声明不会生成 fake dispatch |
| CaptureSession | 跨 turn 持续、finish/cancel/disposed 停止、限额/丢弃/断连透明、进程更新与 PID 复用保护 |
| 图像与坐标 | native/frame 缩放、转屏、geometry mismatch 和 stale ref；证据不充分时 unverified |
| 结果汇总 | 工具成功≠检查通过；日志缺失/清理失败独立；人工确认来源可见；必验项未完成不能全通过 |
| 构建清单 | 删除源码后的旧 lib 文件会被未来构建移除；输出目录边界正确；依赖闭包/配对清单一致 |

可用 fake backend/临时夹具验证以上内部逻辑，但必须标成单元/集成夹具；它们不证明真实手机、性能或界面已通过。读脚本后确认无编译副作用才可运行；其余本轮只提交测试源码和待执行清单。

1. 在隔离目录从修订后的锁文件干净安装、Harmony→E2E 构建、成对 preflight；检查源码与最终产物无 runner 执行残留，缺 e2e 包可冷启动。不要拿旧 node_modules 里“还能跑”作为干净依赖证据。
